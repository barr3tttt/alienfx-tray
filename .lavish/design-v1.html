Two controllers, two protocols

This is the fact that makes every online guide for this laptop contradict itself. The app models them as two independent domains all the way down - separate state, separate error reporting, separate failure.

Keyboard APIv5

Darfon 0d62:cabc
64-byte feature report, report ID 0xCC
SetGlobalEffects(effType, mode, nc, tempo, c1, c2)

One global colour for the whole keyboard. No per-zone: the device reports 0 lights. Per-key is a later probe, not v1.

External APIv4

Alienware AW-ELC 187c:0550
33-byte reports, vendor page 0xFF00
SetPowerAction(lightblock) per light ID

Power-type lights: each carries two colours, AC and battery. SetColor across all 23 IDs does literally nothing - it has to be the power path.

Free feature falling out of the hardware: the two colour slots mean the app can offer "different colour on battery" at zero extra protocol cost. Shipping it in v1.

The trap, and how it is made unreachable

What goes wrong

// AlienFX_SDK.cpp, SetGlobalEffects, API_V5
if (!effType)
    PrepareAndSend(COMMV5_setEffect, {{2, {1, 0xfe}}});

effType 0 sends a clear/disable. The keyboard goes dark in a state setall cannot override. External lights keep responding, so it looks like a half-dead machine. Recovery is a non-zero effType or a reboot.

Why the UI cannot emit it

enum class KeyboardEffect : std::uint8_t {
    Steady = 1,   // confirmed on hardware
};
// every enumerator asserted non-zero at compile time
static_assert(none_of(kAllKeyboardEffects, isZero));

The effect type is a scoped enum with no zero enumerator. There is no uint8_t overload anywhere in the device layer, so "pass 0" is not a value the call site can express - not a runtime if somebody can delete.

Three layers of cover

  • Compile time - a static_assert over the full enumerator list fails the build the day someone adds Off = 0.
  • Unit test - every scheme permutation, including "all off" and pure black, is applied through a fake transport that records every byte. The test asserts effType is never 0.
  • Semantics - "off" is implemented as Steady + black, never as a disable, and brightness is clamped to a 1..255 type so no slider can reach the hardware-off path either.

The other hazard: claiming the device is claiming your keyboard

I confirmed the topology on the machine. The Darfon device has exactly one USB interface: 

5-1  0d62:cabc  iface 5-1:1.0  driver=usbhid  class=03  proto=01  <- 01 = keyboard

The SDK's hidapi is built with the libusb backend, so opening it detaches usbhid from the interface you actually type on. There is no separate LED interface to claim instead. A leaked claim means the built-in keyboard stops working.

Worse still

Mappings::AlienFXEnumDevices() calls hid_enumerate(0,0) and opens every matching path, then throws the duplicates away. Every full enumeration briefly kills typing.

So the app does not use it

It owns its own libusb_context, resolves the one path it wants once, and constructs Functions via AlienFXProbeDevice(ctx, vid, pid, path) directly. Exactly one interface is ever claimed.

  • Handles are opened lazily on first write and closed after 1.5 s idle, so a claim never outlives an interaction.
  • During a slider drag the handle stays open - you are dragging a mouse, not typing - and closes as soon as the drag settles.
  • Close happens in a RAII guard, on the worker's stop path, and on SIGTERM/ SIGINT. If the process is killed outright, the kernel reattaches usbhid when the usbfs fd closes, so the worst case is still recoverable without a reboot.

Decisions you asked me to make deliberately

1. Vendor or submodule the SDK?

chosenSubmodule, pinned

Upstream is alive and is the only thing on the internet that drives both controllers. A submodule keeps provenance, makes every bump an explicit reviewable commit, and keeps ~4k lines of somebody else's C++ out of our diffs.

Vendor a copy

Offline-friendly and patchable in place, but we would silently fork a project we want to track, and every upstream fix becomes a manual merge.

Shell out to alienfx-cli

Rejected outright. A process per colour change makes a slider drag feel like mud and throws away every error the device reports.

The catch: the SDK's FetchContent pulls libusb, hidapi, loguru and json from master/main. Unpinned upstreams mean the build breaks on someone else's Tuesday. Fixed without patching the submodule: we declare all four with pinned tags in our top-level CMakeLists before adding the subdirectory, and CMake's first-declaration-wins rule makes ours stick.

2. Threading model for live preview

One DeviceWorker thread owns every SDK object and every USB handle. The GUI thread never touches libusb, and the worker never touches a widget. They talk only in queued signals carrying plain value types.

GUI thread
  • tray icon, control panel
  • colour wheel drag → emits at most 1 request / 16 ms
  • renders device status banners
  • never blocks, never waits on the worker
applyRequested(Scheme)
→
←
statusChanged(Domain, State)
DeviceWorker thread
  • owns libusb ctx + both handles
  • latest-wins coalescing, older frames dropped
  • 1.5 s idle timer closes handles
  • per-domain failure, never a shared crash

Why latest-wins matters: an external apply is ~36 HID report exchanges for six lights (the v4 power path walks cid 0x5b..0x60 per light), call it 50-100 ms. A drag generates far more frames than that. Queued signals would pile up and the lights would lag seconds behind the cursor. Instead the worker keeps a single pending scheme under a mutex with a generation counter and skips anything stale, so the lights always converge on where the cursor is.

3. How schemes are stored

~/.config/alienfx-tray/
  schemes.json     named schemes
  active.json      what is on right now

Plain JSON, schema-versioned, written atomically (temp + rename) so a crash mid-save cannot leave an unparseable file. An unreadable file falls back to a built-in default rather than starting with no lighting at all.

What it deliberately does not do

  • Does not touch ~/.local/share/alienfx/mappings.json - that belongs to the CLI and stays working.
  • Does not implement -s / save-to-device-memory at all. Login and resume already repaint, so persistence buys nothing and costs the one property that makes this safe to experiment with: a reboot always restores firmware defaults.

4. Login and resume - reusing what is already installed

No second startup mechanism. The existing user unit and the existing system-sleep hook both already call one script, so that script becomes the single seam.

login
alienfx.service
↘
~/.local/bin/alienfx-apply
unchanged path, now a shim
↙
resume
system-sleep/alienfx
exec alienfx-tray --apply        # applies active.json, no GUI, exits
# falls back to the original CLI block if the binary is missing
  • The unit and the sleep hook are not edited. Neither is the user systemd manager - it has no suspend.target, which is exactly why the system-level hook exists.
  • Rewriting the shim is a button in the UI, never automatic, and it backs the original up to alienfx-apply.pre-tray.bak first.
  • --apply and the running tray take the same flock on $XDG_RUNTIME_DIR, so a resume firing while the panel is open cannot have two processes fighting over one USB claim.
